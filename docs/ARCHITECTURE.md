# 系统架构设计

> 印尼行程公款账本 · v3 · 2026-08-24
> 约束与规范见根目录 `CLAUDE.md`（那份是铁律，这份是设计细节）。

---

## 1. 场景与本质

Zachary 是家庭旅行的财政。全家凑一笔公款交给他保管，他代表全体支付共同开销，
每一笔都要让所有人看得见、看得懂、随时可以质疑。

技术上概括：**一个单主写者、多读者、强审计需求的共享账本。**

三个关键判断：

1. **这是账本，不是记事本。** 记错可以改（Zachary 要求保留完整编辑权），
   但每次改动必须留痕并对所有成员公开。
2. **印尼的网络会让「实时」失效。** 景区、山区、车上很可能没信号。
   如果记账时 App 转圈，他会退回手机备忘录，整个 App 就废了。
   **离线可写是核心功能，不是加分项。**
3. **钱不是一个数字，是好几个口袋。** MYR 银行、MYR 现金、IDR 现金
   不能加成一个数，必须分钱包显示。

## 2. 为什么是 PWA

零成本铁律 + 同时支持 iOS 和 Android + 要有推送 → 只剩 PWA。

iOS 上没有任何免费的分发路径：

| 路径 | 能装到家人手机 | 费用 |
|---|---|---|
| App Store / TestFlight | 能 | US$99/年 |
| 免费 Apple ID + Xcode 自签 | **不能**（只能装自己设备，证书 7 天过期，每台要接 Mac） | $0 |
| 第三方侧载 | **不能**（同样 7 天限制） | $0 |

Android 可以自签 APK 直发，但 iOS 封死，所以走 PWA。

### PWA 顺带的好处
没有商店审核。改完推上去，家人下次打开就是新版——包括在印尼旅途中修 bug。

### iOS PWA 的真实限制（必须接受）

| 限制 | 影响 | 应对 |
|---|---|---|
| 推送必须先「加到主画面」 | 只用浏览器看是收不到通知的 | 出发前当面帮每个人装 |
| 需 iOS 16.4+ | 已确认全家满足 | — |
| 本地存储 50MB，7 天不开被清 | 缓存丢失 | 数据在 Supabase，重开自动拉回 |
| 无后台同步 | 离线记的账要等打开 App 才上传 | 每天都会开，可接受；UI 显示「N 笔待上传」 |
| 必须用 Safari 安装 | Chrome 打开没有「加到主画面」 | 发链接时注明 |
| 欧盟 iOS 17.4+ 关闭 PWA 推送 | 不影响马来西亚 | — |

**最大的落地风险不是技术，是「有人没装成主画面」。**
出发前全家聚一次当场装好，比多做两个功能重要。

## 4. 数据模型

| 表 | 作用 | 关键字段 |
|---|---|---|
| `trips` | 一次行程 = 一本账 | 名称、基准币种、起讫日期 |
| `members` | 成员与角色 | 显示名、`role`（owner/admin/member） |
| `wallets` | 钱放在哪里 | 标签、币种、`exponent` |
| `entries` | **账本流水** | `type`、`wallet_id`、`amount_minor`、`fx_rate`、`occurred_at`、`deleted_at` |
| `entry_history` | 每次修改／删除的前后值（触发器自动写） | `entry_id`、动作、before、after、原因、时间 |
| `receipts` | 收据照片 | `entry_id`、storage 路径 |
| `comments` | 家人的提问与回复 | `entry_id`、作者、正文 |
| `push_subscriptions` | Web Push 订阅信息 | endpoint、密钥、成员 |
| `trip_invites` | 邀请链接 | `id`（本身就是邀请码）、`trip_id`、`revoked_at` |

### 家人怎么加入一本行程（2026-08-26 补充）

Owner/admin 在 App 里生成邀请链接（往 `trip_invites` 插一行，`id` 是随机 UUID，
拼进网址 `?invite=<id>`），发给家人。家人打开链接 → 登录（第一次登录会自动建号）→
App 侦测到网址带邀请码，调用 `accept_invite(邀请码)` 这个数据库函数，把自己加进
`members` 表，角色固定是 `member`。

不能直接让家人对 `members` 表做 `insert`——现有规则是"只有 admin/owner 能加人"，
陌生人一开始 `role_level` 是 0，过不了这条规则。`accept_invite()` 用
`SECURITY DEFINER` 绕开这个限制，但只做这一件事：核对邀请码有效、把调用者加成
`member`，不能借这个函数干别的。`trip_invites` 表本身只有 admin/owner 能读写，
接受邀请的人全程不需要（也没有权限）直接碰这张表。

登录邮件的跳转链接要保留住网址上的 `?invite=...`，所以 `emailRedirectTo` 用的是
当前完整网址（`window.location.href`），不是站点根网址——不然邀请码会在
"发信 → 点邮件里的链接跳回来"这个来回中弄丢。

### entries 的 type

| type | 含义 | 方向 |
|---|---|---|
| `contribution` | 成员出资进公款 | + |
| `expense` | 公共消费支出 | − |
| `fx_out` / `fx_in` | 换汇的两条腿（成对出现） | − / + |
| `transfer_out` / `transfer_in` | 同币种搬钱的两条腿（银行提现到现金，成对出现） | − / + |
| `reimbursement` | 还钱给临时垫付的家人 | − |
| `refund` | 退款、取消订单的钱回来 | + |
| `settlement` | 行程结束退还剩余 | − |

`amount_minor` 一律存正数（金额大小），加还是减完全由 `type` 决定——
这样"正负号"只有一个判断的地方（`src/lib/money.ts`），不会散落在各处、也不会存进两个互相矛盾的值。

### 金额存储
整数 minor units，禁止浮点。`exponent`：MYR=2，IDR=0。

IDR 数字很长，UI 必须：千分位分隔、`tabular-nums` 对齐、
**输入超过 7 位数时弹确认**（「你要记的是 Rp 1,850,000 对吗？」）。
餐桌上单手快速输入时最容易多打少打一个零。

## 5. 权限（RLS）

```sql
-- 所有成员都能读
create policy "member_read" on entries
  for select using ( role_level(trip_id) >= 1 );

-- admin 及以上：能增、能改，没有任何限制；
-- 故意不给 delete policy——删除一律走"改 deleted_at"这条软删除路径，
-- 数据库层面直接不允许真删除，避免连带把审计记录也弄丢
create policy "admin_insert" on entries
  for insert with check ( role_level(trip_id) >= 2 );

create policy "admin_update" on entries
  for update
  using      ( role_level(trip_id) >= 2 )
  with check ( role_level(trip_id) >= 2 );

-- 成员可以评论，但只能以自己的身份发
create policy "member_comment" on comments
  for insert with check ( role_level(trip_id) >= 1
                      and author_id = auth.uid() );

-- 只有 owner 能改别人的角色
create policy "owner_manage" on members
  for update using ( role_level(trip_id) >= 3 );
```

### 删除先进回收站，没有"彻底删除"（2026-08-24 定稿）
点删除不是抹掉，而是标记 `deleted_at`，从列表隐藏，进「回收站」页面，可以随时还原。
**不提供"彻底删除/永久抹除"这个选项**——数据库层面直接不允许真删除 entries，
哪怕是 admin 也做不到，因为触发器一定会在这笔账诞生的同时写一条 `entry_history`，
真删除会连审计记录一起抹掉，直接违反"改动历史不可篡改"这条铁律。
账本里的每一笔账，一旦记下就永远留在数据库里，最多是被隐藏，不会真的消失。

### 修改自动留痕
触发器把每次修改和删除的前后值写进 `entry_history`。
**服务对象是 Zachary，不是用来监督他的**：家人问「这笔怎么从 500 变成 450」时，
他点开历史三秒答完。

UI：每笔记录点进去有「变更记录」区块，所有成员可见。列表页给改过的记录一个小标记。
修改时让他填一句原因（可跳过，但建议填）。

### 登录
- **主推：Google 登录**（家人都有 Gmail，点两下就进）
- **备选：Magic Link 邮箱登录**（Supabase 零配置）
- Day 1 先做 Magic Link 跑通链路，Day 2 加 Google
  （Google 需要先在 Google Cloud Console 建 OAuth 应用，步骤琐碎易卡住）

## 6. 多钱包与汇率

### 核心原则
**汇率不是查出来的，是换汇那一刻真实发生的，而且是人输入的。**

- ✅ 每一笔涉及换算的记录都有**可编辑的汇率输入框**，预填上一笔用过的值方便快速记账
- ✅ 记完之后随时可以再改，改动进 log
- ❌ 系统绝不自动查市场汇率、绝不批量重算历史记录

### 必须支持的场景
公款用完，大家再补一笔。这时候：
- 阿姨上个月自己换的，汇率 3,380
- Zachary 昨天换的，汇率 3,420
- 表弟没 IDR，直接给 MYR

**这是三笔独立的 contribution，各带各的币种和汇率。**
不存在「统一汇率」。用第一次收款的汇率去套所有人是错的。

### 换汇怎么记
在兑换店给出 RM 2,000，拿回 Rp 6,800,000 →
写两行：MYR 钱包 `−2,000.00`、IDR 钱包 `+6,800,000`，
实现汇率 `1 MYR = 3,400 IDR` 自动算出并存在这笔交易上。
往后所有 IDR 支出直接扣 IDR 钱包，跟汇率无关。

### 首页显示（2026-08-24 定稿）
首页是「默认钱包 + 可切换」，不是同时摊开显示全部钱包：
- 顶部一个分段控件（标签），列出这个 trip 下所有未归档的钱包
- 默认选中 `wallets.is_default = true` 的那个（这趟去印尼，默认选 IDR 现金——
  这是要天天点钞核对的钱包，不应该还要多点一下才看到）
- 点其他标签切换，查看 MYR 现金 / MYR 银行还剩多少（这两个是偶尔查一下的，
  不需要长期占首屏位置）
- 选中钱包下方是大字余额 + 该钱包的最近记录列表，两者一起随标签切换
- 只有非本地货币的钱包（比如 IDR）才显示"折合约 RM ×,×××（按实际换汇成本）"
  这行小字；MYR 钱包本身就是本地货币，不需要折算

**IDR 现金余额就是口袋里应该有的现金数**，随时可当场点钞核对——旅途中最有用的功能，
这也是为什么默认钱包这么重要：不能让"点钞对账"这个动作还要先切换一次标签。

哪个钱包是默认钱包存在 `wallets.is_default` 字段里，不写死在代码里——
下次旅行如果主要花的不是印尼盾，换一个钱包设成默认就行。

## 7. 结算公式

**该退你多少 ＝ 你交了多少 − 你该承担多少**
（「你该承担多少」= 总消费 ÷ 人数）

### 为什么不用「按出资比例退」
5 人，说好每人 RM 1,000，但 A 交了 RM 2,000（多的先垫着）。
公款 6,000，花了 4,500，剩 1,500。

| 算法 | A 退 | 其他人各退 | A 实际承担 | 其他人各承担 |
|---|---|---|---|---|
| ❌ 按出资比例 | 500 | 250 | **1,500** | 750 |
| ✅ 按人均消费 | **1,100** | **100** | 900 | 900 |

按比例退等于把「谁出得多」变成「谁该多花钱」，但 A 多交的是**暂时垫的**。

验算：`1,100 + 100×4 = 1,500` = 剩余 ✓

**出资相同时两个算法结果一致**，所以直接用正确公式，不用判断情况。

### 结算页
一张表列出每人：交了多少、该承担多少、该退多少。
转完账点确认 → 生成 `settlement` 记录 → 账本归零封账。

## 8. 实时同步 ≠ 推送通知

这是两套机制，都要做。

| | 实时同步 | 推送通知 |
|---|---|---|
| 场景 | 家人正开着 App 在看 | App 关着，手机在口袋 |
| 机制 | Supabase Realtime（WebSocket） | Edge Function → Web Push → 系统通知 |
| 效果 | 列表和余额自动更新 | 锁屏弹出「新增一笔支出 Rp 185,000」 |
| 成本 | $0 | $0（VAPID 密钥自己生成） |

推送链路：插入一行 → 数据库触发器 → Edge Function 取出本次行程所有成员的订阅
（**排除操作者自己**）→ VAPID 签名 → 浏览器推送服务 → 手机。

### 通知要做防抖
一顿饭可能连记 4 笔。每笔都推，家人第三天就关掉通知，监督机制失效。
**记录立即上账（保持透明），但通知做 60 秒合并**：
「新增 4 笔支出，共 Rp 620,000，余额 Rp 4,180,000」。
另外每晚推一条当日汇总——这条才是家人真正会看的。

### Telegram Bot（第二通道，也免费）
全家在用 Telegram。开一个家庭群，机器人往群里播报。

优点：家人什么都不用装、不受 iOS PWA 限制、送达可靠性高。
额外好处：机器人可以**自动把每日汇总和 CSV 账本发进群里**，
顺便解决了「免费方案没有自动备份」的问题。

Telegram Bot API 完全免费。WhatsApp 官方 API 收费，违反铁律一，不考虑。

## 9. 离线优先

**如果只能保住一个进阶功能，保这个。**

- **ID 在客户端生成**：主键是本地生成的 UUID，不等服务器返回
- **本地发件箱**：IndexedDB 存待同步队列。记账只写本地，UI 立刻反馈成功
- **幂等上传**：用 UUID 做 upsert，重发不产生重复账
- **照片同队列**：收据先存本地先显示，联网后再传 Storage
- **可见的同步状态**：每笔带「待同步 / 已同步」小图标

### 单写者红利
协作 App 的离线难在多人改同一条要冲突合并。
实践中主要由一个人记账 → 几乎不会冲突 → 队列顺序发出去就完事。
多 Admin 情况下采用「后写覆盖 + 全程留痕」，不引入冲突合并机制。

### iOS 限制
没有后台同步，离线记的账要等打开 App 才补传。
每天都会开 App，影响很小。但 UI 要明确显示「还有 3 笔待上传」。

## 10. 功能清单

### 核心（必须做）
- 记一笔支出（金额、币种、钱包、分类、说明、时间）
- 实时余额（按钱包分别显示 + 折合基准币种）
- 成员出资记录
- 修改 / 删除（含回收站与留痕）
- 多币种 / 换汇记录
- 收据拍照上传
- 实时同步
- PWA 安装引导
- 离线记账
- 推送通知（Web Push + Telegram）

### 建议加
- 每笔评论 / 提问
- 代垫与报销（公款现金不够时家人先垫，之后从公款还）
- 每日汇总推送
- 分类与统计
- 导出 CSV
- 最终结算表
- 成员管理（Owner 任免 Admin）

### 看情况
- 非均分支出、预算提醒、已读标记

### 明确不做
- 非均分支出（**规则从简：不是全员共享的消费就不走公款，谁玩谁付**）
- OCR 自动识别金额
- 银行 / 电子钱包对接

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 家人没装成主画面 | 收不到通知，监督链条断掉 | 出发前当面帮每个人装。**最大的落地风险** |
| 印尼网络差 | 记不了账 | 离线优先。出发前用飞行模式实测 |
| iOS 推送延迟或丢失 | 家人不知道有更新 | 推送 + 角标 + 未读标记 + 每晚汇总 + Telegram，五层冗余 |
| Supabase 被自动暂停 | 出发前发现连不上 | GitHub Actions 每 3 天 ping |
| 免费方案没有自动备份 | 数据丢了就没了 | 每晚导出 CSV 发家族群（Telegram Bot 自动做） |
| 手机丢失或损坏 | 未同步的记录会丢 | 数据在云端。指定一位家人为备用 Admin |
| 三天做不完 | 赶工出错 | 按功能清单优先级砍。核心做完就冻结 |

### 低科技保险（强烈建议做）
**每晚导出当日账目发到家族群。** 开发成本几乎为零，
但保证即使 App 崩溃、Supabase 挂掉、手机进水，透明度也不会中断——
**而透明度才是这整件事的目的。**
